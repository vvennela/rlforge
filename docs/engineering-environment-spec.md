# AksharaForge engineering environment specification

Status: prototype contract, 26 September 2026. The implementation and intended automated pipeline are distinguished below. This specification does not authorize additional cloud spending or claim engineering-model training has occurred.

## What we are building

AksharaForge turns an engineering drawing into an executable construction task: a model works in a restricted assembly sandbox, receives independently computed rewards, and can be trained on repeated episodes. The experiment asks whether training in generated environments improves performance on unseen designs under the same inference budget.

The viewer displays the environment. A reference build tests that its specification is feasible. Neither is the product's learning result.

The first representation is a simplified LEGO-like stud grid with rectangular parts. It supports static shape and composition tasks: bridges, vehicles and machinery layouts. It does not yet support working engines, rolling axles, real LEGO clutch geometry, load-bearing certification, or arbitrary CAD modeling. A turbine/generator layout is the initial machinery example, not a functioning engine.

## Boundaries: implemented versus required

| Capability | Current state | Requirement for the paper/drawing-to-environment claim |
|---|---|---|
| Original drawing, provenance and extracted artifacts | Local archive/intake retained | Every compiled constraint links to a source page and evidence crop |
| Drawing to executable specification | Three curated abstractions | Compiler emits and validates tasks without per-design handwritten target code |
| Restricted construction tools | Docker worker with place/move/remove | Same interface for any compatible agent |
| Geometry and connection feedback | Deterministic vector, diagnostics and acceptance | Freeze verifier and reward version before comparing models |
| Reference assembly | Procedural, scripted fixtures | Automatically generated feasibility witness, separately labeled |
| Agent episodes | Local Qwen inference-time repair and trace recording | Benchmark construction and repair separately |
| Engineering weight updates | Not implemented or running | Trainer consumes rollouts and rewards; save actual weight changes |
| Engineering uplift | Not measured | Frozen base-versus-trained evaluation on untouched designs |

## 1. Drawing intake and compilation

Input: original PDF/image, source identifier, content hash, page or sheet number, and any supplied units or scale. Preserve the original plus OCR/layout output, image crops, dimension annotations, component proposals and confidence/evidence records separately. Follow the existing Akshara extraction guidelines; do not overwrite raw artifacts with cleaned interpretations.

A compiler must produce a versioned task manifest containing:

- Source hashes and evidence pointers.
- Coordinate system, units, view registration, and permitted transformations.
- Component inventory and required relationships: for example four wheels, two axle stations, wheelbase, support positions, or coaxial rotor and stator.
- Dimensions, tolerances and evidence class for each constraint: **printed**, **calibrated**, **inferred**, or **authored abstraction**.
- Allowed parts, workspace bounds, action budget and termination conditions.
- Executable target regions/constraints, verifier version and frozen reward configuration.
- Deliberately omitted features and the exact scope of a pass.

Printed dimensions take precedence over measuring pixels. Calibrated measurements require a valid scale in the same uninterrupted view. Broken or perspective views cannot silently supply absolute dimensions. Unresolved measurements remain unknown: omit those checks or reject the task; do not invent ground truth.

For a first automated compiler, output a constrained shape/relationship language (boxes, cylinders, rings, repeated components and dimension constraints), not arbitrary verifier code generated by an LLM. A trusted compiler converts that language to geometry and deterministic checks. The compiler may use an LLM to propose an interpretation, but its confidence is not a geometric reward.

Compilation is allowed to fail explicitly. Require valid units, consistent constraints, nonoverlapping target regions where required, legal workspace bounds, and a feasible assembly witness. Keep rejected tasks and reasons. A human can approve a task specification before it is frozen; that makes the task reviewed, not fully automatic.

## 2. Episode contract

`reset(task_id, seed, mode)` creates a fresh workspace. Modes are **construction** from empty and **repair** from a specified corrupted assembly. Their scores are reported separately.

`observe()` exposes the permitted task specification, part palette, current bricks, remaining budget, tool errors and evaluator diagnostics. The existing Qwen adapter receives structured JSON, not drawing pixels. In a future image-conditioned benchmark, record precisely which drawings/crops the agent receives. Do not compare different observation protocols as if they were the same experiment.

`step(actions)` accepts transactional lists of:

```json
{"tool":"place","brick":{"id":"piece1","part":"plate_2x4","x":4,"y":2,"z":7,"rotation":90}}
{"tool":"move","id":"piece1","x":5,"y":2,"z":7,"rotation":90}
{"tool":"remove","id":"piece1"}
```

Coordinates x/y are studs and z is plate heights; one plate is 0.4 studs tall. Rotations are 0 or 90 degrees. The current workspace is 64 × 24 studs × 64 plates; bridge tasks permit 256 pieces and the two assembly tasks 512. A transaction contains at most 512 actions; the included Qwen adapter permits at most 32 per response. These distinct budgets must be recorded. Before benchmarking, check that the complete observation fits the configured model context. The current repair adapter uses 8,192 tokens; larger assembly prompts may require a compact observation protocol or a separately versioned context configuration. Do not silently truncate the task or change the budget between models.

An invalid transaction leaves the previous assembly unchanged, returns an error and consumes a transaction. Success or 16 transactions ends the current prototype episode. Placement is declarative: it can be scored even when not physically insertable in that order. Build-order feasibility is outside this version.

The workspace worker runs without network access in an unprivileged, read-only Docker container. It has the tool implementation, not the verifier or archive. The host owns task validation, scoring and inference. This is a restricted tool sandbox, not unrestricted model-written shell execution.

## 3. Reward and acceptance

The primary output is a **vector**, retained in full per step. Each declared component receives:

| Signal | Meaning |
|---|---|
| Presence | Some matching occupied geometry exists; this alone is insufficient |
| Position | Center-location agreement in physical units |
| Size | Agreement of each bounding dimension |
| Proportions | Agreement of aspect ratios, independent of uniform scale |
| Occupancy overlap | Intersection-over-union with its target region |

Also return source-dimension errors and tolerance checks, whole-shape IoU, overlap/collision counts, and assembly connectivity. Report missing parts explicitly. Correct total length does not excuse absent bridge poles, wheels, a shaft or an exciter.

Current bridge matching segments occupied geometry by height zones and connected regions. Current car/turbine matching compares occupancy in known target regions; off-target cells are assigned to the nearest target bounding box and also penalized by whole-shape IoU. It does not recognize arbitrary components semantically. Agent-supplied names and brick IDs cannot establish correctness.

A dimension score is 1 inside the declared tolerance and falls with normalized excess error. Component proportions convert plate heights to studs. Exact target occupancy is a deliberately strict prototype acceptance criterion. A later constraint-based task may accept multiple geometries, but its acceptance set must be defined before training.

A prototype pass requires all declared components, no collisions, a single stud-connected assembly, source dimensions within tolerance, and no extra target-external geometry. Horizontal face overlap across vertical interfaces constitutes a stud connection; touching side walls does not. This is not a strength or stability analysis.

**Scalar adapter:** the current demo exposes the mean of vector entries, multiplied by 0.25 when validity checks fail. That is a convenience aggregate, not a finalized training objective: families with more components would otherwise have different effective weight distributions.

For the first training experiment, freeze a family-balanced reduction: average the five metrics within each component, then average across components; combine that component score equally with whole-shape IoU and the mean dimension score when dimension checks exist. Missing dimension groups receive no invented score. Apply the same validity gate. Log both this training scalar and every vector entry. Implement and version this adapter before launching training; the current UI aggregate remains explicitly separate.

For an initial episodic trainer, use final episode reward, rather than repeatedly paying the same score for no-op actions. If intermediate shaping is later enabled, specify the transition reward and discount explicitly and test for reward farming. Efficiency rewards for fewer actions/pieces are deferred until correctness learning is established; they must not reward omitting required geometry.

## 4. Reference examples and manual work

A reference assembly is a feasibility witness and verifier test. It may also become a labeled demonstration for an explicitly declared supervised/warm-start arm. Its actor is `scripted_fixture`, never Qwen. Current references are procedurally tiled from curated targets; they are not expert LEGO instructions.

Manual changes to renderer code or a reference fixture are environment development. Manual edits to an agent's assembly are interventions: label them `manual_ui`, preserve the original rollout, and exclude the resulting score from autonomous agent performance. Do not repair model answers between benchmark steps.

Changing a task, reward, target, palette or acceptance tolerance creates a new version. Rerun the baseline under that version; do not count evaluator changes as model improvement. Freeze final-test task content before training and never correct it selectively to favor the trained model.

## 5. Initial task catalog

| Family | Archive | Source-derived constraints | Authored or omitted |
|---|---|---|---|
| Bridge | LoC `ak0443` | Plan spans/width; printed deck and tallest-post datums; calibrated short-post height | Rectangular lower supports, paired posts, thickness; braces, joints and terrain omitted |
| Car | LoC `al1361`, Ford G.P. Pygmy | Length 133.0625 in, width 56 in, height 60 in, wheelbase 80 in | Static voxel tires, floor/fenders and simplified body/seat geometry; no working drivetrain |
| Machinery | LoC `al1187`, Wilson turbine/generator | Component identities and vertical/coaxial arrangement | Dimensions authored; runner blades, hydraulic operation, windings and auxiliary systems omitted |

These three are smoke tests for the interface and verifier. They are not enough to demonstrate general engineering learning. Current parts are rectangular brick proxies, not a full manufacturer part catalog.

## 6. Experiment that would establish learning

Acquire approximately ten independently sourced, usable drawings across the families. Split by **source design**, not just generated dimensions: six training designs, two validation designs and two untouched test designs. Begin with roughly ten variants per design (about 60 training, 20 validation, 20 test instances). This is a small pilot with wide uncertainty, not a robust domain-wide benchmark. The earlier math 80/20 experiment is separate.

Variants may change valid dimensions, omissions and displacements within the declared task language. Different corruptions or scales of one drawing stay in the same split. This avoids presenting memorization of one shape as cross-design transfer.

Before training, run the pinned base model on every evaluation task with frozen prompts, observations, palette, decoding settings, tool budget and verifier. Record construction and repair separately. Keep test references and demonstration traces out of training. The agent may see the specification it must satisfy; the held-out material is the design and solution trajectory, not the task statement.

Train the same open model on training episodes only. Start with a bounded pilot of 100 optimizer updates, four sampled rollouts per prompt, and validation checks at 25/50/100 updates; this is an initial budget, not a convergence guarantee. The trainer implementation and compute budget require a separate run configuration. Select a checkpoint on validation, then evaluate once on the untouched test set using the same inference protocol as baseline.

Primary metric: complete-task success rate. Secondary metrics: per-component correctness, dimension errors, collision/connection validity, tool/token cost and construction versus repair performance. Report counts, paired task outcomes and uncertainty, not only mean scalar reward. Count failed parsing, invalid actions, timeouts and unfinished assemblies as failures under a frozen policy.

Distinguish these comparisons:

1. Frozen base agent versus weight-updated agent under identical observations and budgets: evidence of learning if held-out performance improves.
2. Base agent with more repair attempts or reference demonstrations versus base agent without them: inference-budget or context benefit, not weight improvement.
3. If reference demonstrations train the model, compare demonstration-only training with demonstration-plus-RL before attributing the gain specifically to RL.
4. Compiler success and fidelity on unseen drawings: a separate measure of automatic environment generation. Solver uplift does not prove compilation accuracy.

Broader benchmark retention checks are desirable after actual weight training. There is no basis yet to claim the engineering model improves, transfers to working engines, or preserves every other capability.

## 7. Portable artifacts and completion gates

A standalone task bundle must contain the manifest, hashes/evidence map, geometry/constraint description, permitted palette, verifier/config version, deterministic seeds, and separately labeled reference/corruption fixtures. Source assets should accompany it when redistribution is permitted; otherwise include their exact retrieval provenance. No host-specific absolute path belongs in the task contract.

Each run retains model/revision, prompts, outputs, actions, tool errors, observations, all rewards, termination reason, timing and configuration. A training run additionally retains optimizer configuration, adapter/checkpoint hashes and evidence of weight updates. Logs of model-written explanations are outputs, not access to hidden internal reasoning.

Completion gates:

- **Environment ready:** references pass; missing/shifted/extra/overlapping components fail; renaming bricks cannot change geometry rewards; invalid actions are atomic; sandbox tests pass.
- **Automatic compiler demonstrated:** previously unseen drawings compile without per-drawing target code; evidence is auditable; invalid inputs are rejected; accepted tasks have feasible witnesses.
- **Learning demonstrated:** a saved trained checkpoint beats the pinned baseline on untouched designs under the same budget, with failures and uncertainty reported.

The competition demo should name the gate actually achieved. Today the deliverable is a curated environment prototype; automated compilation and measured engineering uplift remain required experiments.
